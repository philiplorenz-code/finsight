# Backend integration contract

API prefix `/api`. All monetary JSON fields are decimal strings; dates ISO-8601. Authenticated endpoints use the `finsight_session` HttpOnly cookie. `/auth/me` and login/setup return `{id,email,csrf_token}`; mutating requests require `X-CSRF-Token` (setup/login exempt). Single owner setup requires body `bootstrap_secret,email,password` and `FINSIGHT_BOOTSTRAP_SECRET` environment variable.

## Python integration (stable)

`app.db`: `Base`, `get_db()` dependency, `SessionLocal`, `engine`. SQLAlchemy 2 synchronous sessions.
`app.auth`: `current_user` FastAPI dependency returning `app.models.User`; `require_csrf` global dependency handles mutations and authentication exceptions. `app.config.settings` environment configuration.
`app.locking.lock_owner(db,user_id)` is the shared financial mutation boundary. `ingest` calls it internally before its first import/account/transaction lookup, including duplicate-file handling. HTTP and watched-file callers must not implement independent import locking. PostgreSQL uses `users FOR UPDATE`, requires READ COMMITTED isolation, and refreshes previously cached owner financial rows after acquiring the lock. SQLite takes a write lock via a no-op owner update before financial reads. Allocation, account and bucket mutations use the same owner-first lock order; worker claim-row fencing may precede the owner lock. The lock is held through import reconciliation and commit. Live PostgreSQL concurrent interleavings remain centrally verified, not inferred from SQLite tests.
`app.models`: `User(id,email,password_hash,created_at)`, `Account(id,user_id,source_key,name,currency,included,ownership,purpose,inactive)`, `Transaction(id,user_id,account_id,source_key,booking_date,value_date,amount,currency,merchant,description,category,category_override,is_transfer,transfer_uncertain,split_parent_key,split_role,contract_name,tags,source,import_id,missing_from_latest,created_at)`, `Import(id,user_id,filename,sha256,status,row_count,created_at,summary)`, `Finding(id,user_id,title,body,kind,status,evidence,created_at)`, `Setting(user_id,data)`. IDs strings UUIDs. `Transaction.source` is sensitive raw source data and must not go to external providers. Additional models belong to integration modules and may subclass `Base`.

AI/jobs owner: expose FastAPI `router` from `app.ai` and `app.notifications` (paths `/ai/chat`, `/ai/usage`, `/notifications/test`, etc., WITHOUT `/api`); main mounts available routers with `/api` and global CSRF. Each endpoint must depend on `current_user`. `app.jobs` may define worker entrypoint. No app.ai/jobs/notifications files are created by API owner. Backend startup imports these modules if present to register their tables before migration/test create_all.

## Routes and responses

- GET `/health`: `{status:"ok",database:"ok"}`
- GET `/auth/status`: `{initialized:bool,authenticated:bool}`
- POST `/auth/setup`, `/auth/login` → user + csrf above. POST `/auth/logout` → `{ok:true}`. GET `/auth/me` → user + csrf.
- GET `/overview?start=YYYY-MM-DD&end=YYYY-MM-DD`: `{currencies:[{currency,income,expenses,surplus,savings_rate,observed_balance,liquid_balance,nominal_allocated,allocated,funding_shortfall,available_liquidity,monthly_obligations}],categories:[{currency,category,amount}],trends:[{month,currency,income,expenses,surplus}],warnings:[str],start,end}`. Future booked movements omitted; internal transfers and split parents excluded conservatively. `allocated` is currently backed funding, not nominal allocation intent; `available_liquidity = liquid_balance - allocated` and may be negative.
- GET `/accounts` → array of account objects `{id,name,currency,included,ownership,purpose,inactive,source_key,balance,balance_date,warnings}`; PATCH `/accounts/{id}` editable name/included/ownership/purpose/inactive. GET `/accounts/{id}/balances` → observation array.
- GET `/transactions`: `{items:[transaction],total,page,page_size}`; filters `search,start,end,account_id,category,min_amount,max_amount,merchant,is_transfer,contract,tag,currency`; GET `/transactions/{id}` includes source and revisions. PATCH `/transactions/{id}` accepts `category_override` nullable and `tags` string array (at most 50 nonempty tags, each at most 100 characters). POST `/transactions/{id}/reset` clears override.
- POST `/imports/preview`: multipart `file` → `{row_count,columns,unknown_columns,warnings,accounts}` (no raw preview records). POST `/imports` multipart `file`, optional form `full_snapshot=false` → import object. GET `/imports` → import array; GET `/imports/{id}` → import object. Identical hash returns previous import with `duplicate:true`. Processing is synchronous and persistent; uploads are not retained for retry.
- GET `/buckets` → array including linked allocations, obligations and `{nominal_allocated,funded,funding_shortfall,monthly_obligation,required_monthly_contribution,warnings}`; POST `/buckets` body `{name,currency,kind:"virtual"|"real",target?,due_date?}`; PATCH/DELETE `/buckets/{id}`. PUT `/buckets/{id}/allocations` body `{allocations:[{account_id,amount}]}` replaces allocations atomically and rejects reuse/negative/unowned funds. Each returned allocation includes `{amount,backed_amount,funding_shortfall,funding_status,warnings}` in addition to its IDs; status is `backed|partial|unbacked|ineligible|unobserved`. POST `/buckets/{id}/obligations` body `{name,amount,period:"monthly"|"quarterly"|"yearly"|"once",due_date?,scheduled_contributions?}`.
- GET `/contracts` → `{items:[{name,currency,source,confidence,period,annual_cost,monthly_cost,next_charge,price_change,evidence}],warnings}`.
- GET `/findings` → array; PATCH `/findings/{id}` `{status:"open"|"acknowledged"|"dismissed"}`.
- GET `/settings` and PATCH `/settings` → settings JSON. Defaults locale de, timezone Europe/Berlin, currency EUR, AI disabled; optional integration-specific keys stored verbatim, no provider secrets exposed by API.

## Implemented integration configuration

`PATCH /settings` accepts a complete nested `ai` policy: `enabled`, `external_consent`, `proactive_consent`, `model`, `prices` (map from allowlisted model to `{input:"EUR-per-million",output:"EUR-per-million",currency:"EUR",verified:bool}`), decimal-string `total_limit`, `monthly_limit`, `run_limit`, `channel_limits` (`chat`, `weekly`, `monthly`, `changed_import`), and bounded `max_concurrent`, `max_input_tokens`, `max_output_tokens`, `max_tools`, `max_steps`, `timeout_seconds`. Pricing is owner/operator maintained; missing verified pricing fails closed. The AI module additionally enforces operator environment gates and pricing; nested settings cannot bypass those gates. Legacy/null/non-EUR persisted policies are not silently relabeled EUR. Provider credentials are environment configuration, not part of this API. Legacy booleans change existing policies only, and cannot enable an unconfigured integration. The AI integration also owns dedicated `/ai/settings` routes and explicit environment-backed consent provisioning.

Nested `notifications` replaces the notification preferences: `enabled`, `server`, `topic`, `timezone`, `quiet_start`/`quiet_end` (minutes after midnight), `stale_after_hours`, `events` (`weekly`, `monthly`, `report_ready`, `anomaly`, `import_changed`), `reminder_hour`, `reminder_minute`, `weekly_day`. Successful imports update freshness and can enqueue opted-in `import_changed` notifications; no delivery occurs in the upload request. GET `/notifications` returns `{items:[{id,event,state,reason,attempts,created_at,sent_at}]}`. AI usage exposes EUR budget liabilities with explicit run currency. A disabled optional integration remains mounted and reports an honest disabled/suppressed state.

Settings and ordinary request bodies are bounded at 64 KiB; multipart uploads have a streaming request-body limit plus the stricter file-byte limit. Auth rate limits persist in SQL (ten attempts per client address per fifteen minutes). No forwarded client-IP header is trusted by application code. Secure cookies are enabled by default; local HTTP development requires `FINSIGHT_COOKIE_SECURE=false`.

## Delivery notes and verification boundaries

Exact aliases for all 29 documented source headers are supported; every source column is retained, with unknown columns additionally in `source.unknown`. Declared contract periodicity is used when recognized. Unknown split-type values are retained and visibly warned rather than guessed. Normal bookings carrying `Referenz-Original-ID` alone are not presumed split children. Stable account and booking IDs are hashed for normalized identity; raw source data remains private in authenticated transaction detail. A fallback without booking IDs preserves duplicate occurrences and warns about identity ambiguity.

Numeric XML lexemes are captured during the bounded, defused ZIP/XML preflight before openpyxl decoding. Monetary normalization uses `Decimal(original_xml_text)`; `source.columns` and `source.unknown` retain exact numeric spelling, including trailing zeros and scientific notation. openpyxl is used for workbook structure, strings and Excel date/epoch interpretation, not monetary float-to-string conversion. Accepted monetary values fit NUMERIC(24,8) (absolute value below 10^16, no more than eight decimal places); values outside that contract are rejected, never silently rounded. Source classification and derived classification are separate: every import rebuilds all owner's split/transfer inputs from immutable source columns, then reconciles groups. Removing a relationship restores former parents and removes inherited transfer flags; unchanged and overlapping partial imports cannot perpetuate stale derived roles.

### Bucket backing and contribution policy

Allocation `amount` and `nominal_allocated` preserve user intent. Only included, explicitly owned, non-investment, same-currency accounts can back buckets or contribute to observed available liquidity. Their latest non-future observed positive balance is capacity. Negative balances remain negative in `liquid_balance` and `available_liquidity`; they simply cannot back positive allocations. Account exclusion/ownership/purpose changes are reversible and retain allocation intent, but immediately invalidate backing. Balance drops cap backing at observed capacity. Capacity is distributed once across all owner buckets, ordered by stable bucket UUID ascending (then allocation UUID); this is explicit priority, not a claim of chronological creation priority or proportional funding. All bucket and overview responses use the same backing calculation, with underfunded/ineligible/missing-balance warnings. `funded` and `allocated` never count the same backing twice; nominal intent beyond backing is reported as `funding_shortfall`, not funded money.

For obligations, effective due date is `obligation.due_date or bucket.due_date`; missing dates are conservatively treated as immediately due. Obligations are ordered by effective date then stable obligation UUID. `scheduled_contributions` is obligation-specific funding explicitly expected to arrive by that debit's due date, not a dated schedule engine or a booked expense. First compute `remaining_debit = max(0, amount - scheduled_contributions)`, then consume shared **backed** bucket funds once, then divide the remaining gap by contribution periods. Excess scheduled contributions never fund another obligation. This scalar timing assumption is explicit; dated contribution records remain future work. Required contributions must not be reduced by nominal but unbacked allocations.

Invalid parsed imports appear in history as `failed` with safe generic errors. Processing is synchronous, not a durable upload queue: source files are not retained; retry means re-upload. Full snapshot intent is advisory and cannot delete records. Multiple same-day balance observations use the final source row and warn about unverified intraday order. As-of balances never look forward; current allocations are not presented as historical allocation facts. Investment-purpose balances do not count as liquid funds and cannot fund liquidity buckets.

Migration `0001` freezes the core and integration schema independently of application model evolution. Before first public release its snapshot was synchronized with the AI owner's nullable `ai_policies.budget_currency`, nullable `ai_runs.currency`, and `notification_settings.reminder_minute` additions; the finance review fixes require no new columns. Already-created experimental databases must be deliberately migrated/recreated by their operator rather than assuming an edited historical migration runs again. SQLite upgrade/schema comparison/downgrade and PostgreSQL offline SQL compilation are automated. PostgreSQL live locking/concurrency, clean Compose deployment/restore, actual external-provider billing and actual ntfy delivery require separate integration verification. Forecasts, volatility, emergency coverage without essential-cost classification, historical allocation snapshots and automated arbitrary split-type interpretation are not claimed implemented. Historical views use current account inclusion/purpose and current planned obligations, with unversioned classification/allocation limitations rather than a complete historical portfolio reconstruction.
